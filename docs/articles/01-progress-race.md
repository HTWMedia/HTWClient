# 任务明明跑完了却永远卡在 100%：`Progress<T>` 的一场竞态

## 现象

我们的视频渲染流水线有个异步任务：提交后拿到 `taskId`，前端每 3 秒轮询一次状态。
某天线上反馈：**任务进度走到 100% 之后就再也不动了**，状态一直是 `running`，
直到 30 分钟后系统自己报超时。

诡异的是——**同样的代码，本地跑 52 秒就正常出片**。

## 第一反应（错的）

我们一开始怀疑的是上游：远程渲染是不是慢了？是不是某个回调没回来？
于是去翻渲染服务的日志、去查网络。查了半天一无所获。

真正的线索藏在三条日志特征里：

1. 轮询日志密密麻麻，但**从头到尾没有一条 "pipeline completed"**；
2. 任务状态里，`step` 停在最后一条**进度文案原文**（比如"合成中…"），
   而不是结束时应该写入的"完成"；
3. `resultPath` 是空的。

第 2 条是关键：如果 `Complete()` 根本没执行，那 `step` 应该停在更早的地方；
它停在最后一条进度原文，说明——**`Complete()` 执行过了，但状态又被别的东西改回去了**。

## 根因

代码长这样（简化）：

```csharp
var progress = new Progress<string>(msg =>
{
    state.ProgressLog.Add(msg);
    state.Status = "running";   // ← 问题在这
});

await pipeline.RunAsync(progress);
state.Status = "completed";     // Complete()
```

`Progress<T>` 的回调**不是同步执行的**。你调用 `Report(...)` 时，回调被投递到线程池，
什么时候跑、跑多久，都不保证。也就是说：

- 流水线里最后一次 `Report("合成中…")` 发出去；
- 流水线返回，`Complete()` 把状态写成 `completed`；
- **这时那个迟到的回调才被执行**，它无条件把 `Status` 又写回 `running`。

任务就此"复活"成一个永远跑不完的任务。

**为什么本地不复现？** 本地 52 秒，最后一条进度报告在 `Complete()` 之前就落地了。
线上 134 秒，慢了近三倍，迟到的概率大幅上升。**渲染越慢，越必现** ——
这也是这类 bug 最烦人的地方：它不是"偶发"，是"在你最慢的环境里稳定复现"。

## 修法

一行判断的事：任何写进度的入口，先判终态。

```csharp
private static bool IsTerminal(TaskState s) =>
    s.Status == "completed" || s.Status == "failed" || s.Status == "cancelled";

var progress = new Progress<string>(msg =>
{
    state.ProgressLog.Add(msg);
    if (IsTerminal(state)) return;   // 终态之后，迟到的进度只记日志，不改状态
    state.Status = "running";
});
```

同样的保护要加在每一个"更新进度"的方法上——我们这里有三个入口
（两个任务管理器 + 那个回调），漏一个就会以另一种形式复发。

## 怎么防止再犯

补两个方向的测试，缺一不可：

1. **终态之后再报告进度，状态不能被改回 `running`**（这是 bug 本身）；
2. **任务运行期间的进度照常生效**（防止有人把保护写过头，一上来就 `return`，
   导致任务永远停在 `pending`）。

第 2 条很多人会漏。守卫写错方向的后果是"任务压根不开始跑"，比原 bug 更难查。

## 带走的结论

- **`Progress<T>` 的回调顺序和时机都不保证**，别在回调里写"无条件覆盖"的状态机。
- 任何"进度更新"入口都应该先判终态再写状态。这条规则值得写进你们的项目约定里。
- 排查"卡住"类问题时，先分清两件事：**是没执行完，还是执行完了被改回去**。
  看状态里停在哪条文案，比看"卡了多久"有用得多。
- 本地不复现、线上必现，先想"时间差"而不是"环境差异"。
