# 三端同构：桌面端、CLI、Web 共用一套 API 契约怎么不烂

## 现象

我们的后端是一套 `/api/v2/*`，前端却有三个：

- **桌面端**（Electron，主产品）
- **Agent CLI**（给自动化/Agent 调用的命令行）
- **Web**（浏览器直接访问，覆盖 macOS / Linux）

某次给"智能包装"能力加了参数，我在桌面端改完，跑通了，发布。
两天后用户反馈：**CLI 里这个功能还是旧行为**。

一查才发现——三端各实现了一遍这个能力，**我只改了其中一处**。

## 为什么会有三份

不是我们喜欢重复。三端的运行环境和交互模型真的不一样：

- 桌面端要处理文件选择、进度条、任务轮询、402 横幅；
- CLI 要能非交互跑完，输出结构化结果；
- Web 没有本地文件系统，走另一套上传通道。

但**业务语义是同一套**：同一个端点、同一份契约、同一个账号、同一份配额。
差异应该在"呈现层"，不该渗透到"调什么接口、传什么字段"。

## 第一反应（错的）：写个文档让大家记得同步

我们确实写了文档，开头一句"改接口记得同步三处"。
**这类约定三个月内必然失效**——人总会忘，而且忘了之后没有任何机制会告诉你。

## 真正的做法：把能力往后端收

后来我们定了条规矩：

> **要把一个能力搬到第二个端时，先看后端有没有现成的 Service；没有就抽一个出来，
> 别在前端复制第二份实现。**

举个例子。智能包装原本在 Web 侧有一份实现，桌面端要加同样的功能时，
我们没有照抄，而是把逻辑抽成后端的 `SmartPackagingService`，两端都调它。
同理，短剧的"动态镜头"能力从视频创作服务里抽成了公共的 `ShotVideoResolver`。

这样带来的最大变化不是省了几行代码，而是：**判断"一个能力应该长什么样"的地方只剩一个**。

## 契约层面的三个纪律

**1. 大小写规矩要写死，别靠试。**

后端用 Newtonsoft 的默认契约解析器，响应里的字段是 **PascalCase**；
但桌面端有一层 camelCase 归一化（为了页面里写得顺手）。于是同一个字段在
不同层级看起来不一样：

```js
// 走归一化层的响应：camelCase
const id = data.taskId;

// 但 JSON.parse 出来的嵌套字符串不经过这层，仍是 PascalCase
const artifact = JSON.parse(data.Artifact);
const title = artifact.Title;    // 不是 artifact.title
```

这条"嵌套字符串不被改写"的规则，**是我们最高频的 bug 来源**，
现在写进了项目约定：读字段前先确认它来自 POCO 还是匿名投影。

**2. 统一入口，禁止直连。**

桌面端曾经有两条调用路径（`htw.call` 和 `HTWApi.call`），
前者不带头信息，用错就 401 且看不出原因。现在统一走一个入口，
其他路径要么删掉、要么只保留给白名单来源。

**3. 三端各写一个冒烟，而不是靠人联调。**

真机联调的成本高到不可持续（尤其是 Electron），我们改成
**三个端各自跑冒烟脚本**对准同一套真实后端（详见本系列另一篇 jsdom 冒烟）。
冒烟覆盖不到的差异，会在下一次改动时以 bug 的形式冒出来——
但至少它冒出来的时间从"用户发现"提前到了"我改完就能发现"。

## 还做不到的事（诚实说）

- **没有自动化的"三端一致性"检查**。我们现在能做的是"改接口时同步 grep 三处"，
  靠清单而不是靠工具。这是已知的缺口。
- **能力覆盖本来就不一样**：有些能力只有桌面端有，有些只有 CLI 有。
  我们接受"覆盖不同"，但要求**契约相同**——同一个端点在三端的行为必须一致，
  至于谁暴露这个能力，是产品选择。

## 怎么防止再犯

- 抽 Service 时顺手加一个**参数守卫测试**：比如 multipart 端点每个简单类型参数都必须标来源
  （漏标会静默取默认值）。这类静态扫描测试跑几毫秒，能挡住一大类回归。
- 新增端点时，**在契约文档里写清三端的支持情况**，别让人猜。
- Code Review 时专门问一句："这个改动影响哪几个端？"

## 带走的结论

- **"记得同步"不是机制**。要么让只有一处可改，要么让改动能被自动发现。
- **差异放在呈现层，业务语义往后端收**。抽 Service 的收益不在复用，在于把判断点收敛成一个。
- **契约的细枝末节（大小写、空值、嵌套结构）才是真正的坑**，功能层面的差异反而好发现。
- 接受"三端覆盖不同"，但**同一端点的行为必须一致**——
  用户能容忍某端没有这个功能，容忍不了同一功能在两端表现不同。
