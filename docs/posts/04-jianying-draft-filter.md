# 草稿渲出来了，滤镜为什么没生效

> 关键词：剪映草稿 结构、滤镜 不生效、草稿解析、云端渲染、像素对照
>
> 备选标题（A/B）：「剪映草稿里的滤镜，到底写在哪才有效」
> 首发建议：公众号（长文），之后按平台改写标题转掘金 / 博客园。

## 一、「渲出来了」和「渲对了」是两件事

我们用 Python 把一段素材拼成剪映草稿，提交到云端渲染，任务返回成功，成片下载下来，时长、分辨率、音轨都对。打开一看：说好加的滤镜，一点没变。

更麻烦的是它不报错。没有红字，没有失败任务，没有「资源不存在」的提示。整条流水线每一步都是绿的，只有最后的画面不对。

这类问题最容易把人带进死胡同：先怀疑资源包没上传，再怀疑会员权限，再怀疑资源标识过期，一路查下去全都有合理解释，也全都查不出毛病。我们前后花了两轮复测才把真因锁死，结论是——**问题不在「有没有这个资源」，在「草稿里那几行 JSON 是怎么写的」**。

一句话定义这件事：剪映草稿是一个 JSON 工程文件，云端渲染器只认编辑器自己写出来的形态；手写草稿时只要形态和它对不上，渲染器不会报错，而是**静默跳过**这一层效果。

## 二、先建立正例，再谈排查

前几轮都是反证（排除 id、排除会员、排除资源包），越排越没底。真正让局面翻转的是换了个方向：**先证明云端确实支持滤镜**。

我们直接用剪映网页版，给同一段彩条素材加「彩果」，导出成片，量同一帧：

| | 饱和度 | 亮度 |
| --- | --- | --- |
| 无滤镜基线 | 192 | 122 |
| 网页版加「彩果」 | **135.5（−29%）** | **92** |

滤镜确实会被云渲染。而且官方创建渲染任务时的 `app_version=11.5.1`、`sdk_version=15.7.0` 与我们提交的参数完全一致——**云端能力是同一套，差的只有草稿形态**。

这一步很关键。它把「是不是不支持」变成了「我们写错了哪里」，问题从一个黑盒变成了一份可以逐字段对照的请求体。

## 三、抓包对照：官方草稿里滤镜长这样

下面是网页版保存草稿时，滤镜素材的真实形态（省略无关字段）：

```json
{"id":"72681E82-...","effect_id":"7507484","resource_id":"7175127220808061477",
 "name":"彩果","type":"filter","sub_type":"none",
 "path":"/editor/effect/filter/7175127220808061477",
 "value":1,"category_id":"39535","category_name":"selected",
 "platform":"all","apply_target_type":0,"source_platform":0}
```

和我们当初手写的版本比，有四处相反：

| # | 维度 | 官方 Web 草稿 | 我们原来的写法 |
| --- | --- | --- | --- |
| 1 | 素材位置 | 留在 `materials.effects`，整份草稿**没有** `filters` 键 | 单独建 `materials.filters` 桶 |
| 2 | `effect_id` | **7 位短标识**（彩果 `7507484`） | 直接填 19 位的 `resource_id` |
| 3 | `path` | `/editor/effect/filter/<resource_id>` | 清空，或误用视频特效的 `effects2` 路径 |
| 4 | 挂接方式 | 独立 `type="filter"` 轨道，段用 `material_id` 直指滤镜素材 | 把滤镜 id 塞进每个视频段的 `extra_material_refs` |

顺带说一个很容易忽略的点：官方草稿里，**视频段的 `extra_material_refs` 不含滤镜 id**。也就是说滤镜不是「贴在片段上的属性」，而是一条独立轨道上的独立素材。按「给片段加个效果」的直觉去写，就会自然写错。

第 2 条是决定变量。我们后来把三条滤镜全按官方形态摆好（位置、路径、独立轨全部对齐），只让 id 位数不同：

| 段 | 滤镜 | `effect_id` | 与基线段的像素差 |
| --- | --- | --- | --- |
| 1 | 无（基线） | — | 0.000 |
| 2 | 彩果 | **7 位** `7507484` | **10.463** |
| 3 | 去黄增质 | 19 位 | 0.056 |
| 4 | 空灵 | 19 位 | 0.056 |

同一份草稿、同一条管线，只有短标识那段出效果。0.056 是编码噪声，10.463 是两个数量级之外的真实差异。

## 四、改对形态之后，还有一个更隐蔽的坑

按上面四处改完，手工探针草稿终于出效果了：同一帧的 R−B 从 −5.21 走到 −9.69（红色被压、蓝色抬升），像素差 10.639；两条不同来源路径（素材放在 `filters` 桶 / `effects` 桶）结果一致，说明桶位置会被服务端归一化，**真正起作用的是形态改写本身**。

我们当时把结论写成了「修好了」。结果真实创作出片时，滤镜还是没有。

原因是两条链路：

```
手工探针：草稿 → 导出接口 → 模板链路（会调用形态改写）→ 云端渲染
真实出片：创作流程 → 组装草稿内容 → 直接上报 → 云端渲染
```

形态改写只挂在第一条链路上，第二条从头到尾没调用它。配置读到了，草稿里也有滤镜素材，但那份素材仍是旧形态，云端照旧静默跳过。用生产链路做对照渲染，两片逐像素相同（差异 0.0000，连成片字节数都是 333296）。

把改写补到两条构建路径的公共出口之后，同一份最终代码再跑一次：

| 段 | 无滤镜 R−B | 加滤镜 R−B | 像素差 |
| --- | --- | --- | --- |
| 1 | −113.09 | −68.69 | 18.1180 |
| 2 | −113.26 | −68.36 | 18.2865 |
| 3 | −115.46 | −70.12 | 18.2765 |
| 4 | −113.26 | −68.36 | 18.2865 |

成片字节数 333296 → 306038。这次才是真的生效了。

**教训比 bug 本身更值钱**：「修好了」要按调用链确认，不能按「函数写对了」确认。以后给草稿加任何形态规则，都得在两条出口各查一遍，再用生产链路（不是手工拼的探针草稿）做一次对照。

## 五、「渲染成功 ≠ 有效果」：怎么把静默失败量出来

静默失败没有日志可看，只能靠像素。我们把摸索出来的判读口径列在这里，它比某个具体字段更通用：

1. **必须按帧号抽帧，不要用秒数定位。** `ffmpeg -ss 3` 这种写法在带转场的片子上会骗人——渲染帧率可能是 29.77fps，两片「同一秒」根本不是同一帧，算出来的差异能到 23dB 的假信号。用 `select=eq(n,90)` 这种帧号表达式才对齐。
2. **先量噪声基线。** 同一草稿渲两次，或渲一份全无滤镜的对照，才知道「多大算真差异」。我们 26 段全无滤镜的对照里，段间差异落在 `0.0179~0.0189`；而生效值在 4～36 之间。
3. **留足余量。** 云端调色不是逐位可复现的，同一草稿两次渲染，滤镜段自身能飘到 0.2965。别拿 0.1 级别的差异下结论。
4. **同源多段，一次测完。** 让 26 个片段复用同一段源素材（`source_timerange` 都指向 0～1.2s），只有滤镜不同，段 0 当基线，一次渲染就能把 25 条滤镜全验完。

最后那条让我们拿到了一份可以放心用的清单：25 条精选滤镜逐条云渲染对照，**25/25 生效**，最小的「亮肤」像素差 4.0015，最大的「樱粉」36.6899，服务端日志确认「素材 25 条 / 滤镜轨段 25 个」。节选：

| 滤镜 | 短标识 | 像素差 | 滤镜 | 短标识 | 像素差 |
| --- | --- | --- | --- | --- | --- |
| 亮肤 | 2938869 | 4.0015 | 清晰 | 2938813 | 9.5943 |
| 冷蓝 | 2938823 | 4.6491 | 暮色 | 1362560 | 15.5783 |
| 净透 | 2938816 | 13.6597 | 橙蓝 | 2938824 | 12.4892 |
| 彩果 | 7507484 | 9.6113 | 高饱和 | 1362680 | 11.8556 |
| 暗夜 | 1362562 | 26.2037 | 黑金 | 1362502 | 19.1948 |

> 这些数字只说明「该条在同源彩条素材上确实改变了像素」，不代表强度可以跨素材比较——差异大小和素材本身的色彩分布有关。

## 六、两条走不通的路，也一并记下来

排查里最有价值的往往是否定结论，能省下后来者几天时间。

**其一：19 位标识的滤镜在这个链路上用不了。** 目录里的另外 215 条滤镜，`effect_id` 和 `resource_id` 是同一个 19 位值，找不到 7 位短标识。我们找过第二个来源：素材详情接口返回的 `effect_id` 本身就是 19 位，分类接口只认 `category=selected`，传其他分类一律返回 `200501`。短标识没有别的入口，这 215 条暂时无解。

**其二：纯参数调色在 Web 链路上没有对应形态。** 你可能会想「不挑资源，直接写亮度、对比度、饱和度的值不就行了」。我们把这套参数放进两种素材桶、两种挂法，四种组合的像素差全在 0.054～0.058，等于噪声。旁证更硬：

| 取证对象 | 结果 |
| --- | --- |
| 官方保存草稿请求体的 39 个 `materials` 桶 | 既没有 `filters` 也没有 `adjusts`；`hsl` / `color_curves` / `material_colors` / `primary_color_wheels` / `log_color_wheels` 五个调色桶都在，但**全是空数组** |
| 官方 Web 打包草稿（47 个桶） | 五个调色桶 + `effects` 全空，片段上只有 `enable_hsl` / `enable_lut` 这类默认开关 |
| 仓库 422 份 JSON + 本机 1257 份剪映草稿 | 没有任何一份在这五个桶里写过真实调色内容 |
| 开源草稿库 `pyJianYingDraft` | 五个桶写死为空数组；`adjust_params` 是特效参数实例，不是调色容器 |
| 接口探测 | `panel=filter&category=selected` 可用；`adjust` / `adjustment` / `color` / `regulate` 一律 `200501` |

结论不是「参数写错了」，是**这条 Web 渲染链路既没有可照抄的参数化调色草稿形态，也没有可以枚举参数的面板接口**。继续猜字段名只会重复一次静默无效。想调色，目前可靠的是选一条真实存在的资源型滤镜；需要精细数值时，先用 ffmpeg 把效果烧进素材再进草稿。

## 七、什么时候能照这篇做，什么时候不能

| 场景 | 结论 | 说明 |
| --- | --- | --- |
| 手写剪映草稿交给云端渲染，滤镜不生效 | ✅ 适用 | 先按第三节四处对照形态，重点看 `effect_id` 位数 |
| 25 条精选滤镜（7 位短标识） | ✅ 可用 | 已逐条云端对照，25/25 生效 |
| 目录里其余 215 条 / 自定义 LUT 资源 | ❌ 不适用 | 无短标识，云端静默跳过 |
| 直接写 `brightness` / `saturation` 数值调色 | ❌ 不适用 | Web 链路无对应形态，见第六节 |
| 转场、贴纸、视频特效等其他素材类型 | ⚠️ 形态各不同 | 转场用目录现采标识；视频特效同样要求 7 位短标识，但路径段与滤镜不同，不能照抄这张表 |
| 在编辑器里预览草稿看效果 | ⚠️ 不作依据 | 编辑器预览不代表云端产出，判读一律以成片抽帧为准 |
| 想确认「我这次到底生效没有」 | ✅ 必须做 | 按帧号抽帧 + 无滤镜对照，别看日志 |

## 八、三行命令自己跑一遍

我们把这个流程做成了一份可复现的示例，用 `pyJianYingDraft` 生成草稿、提交云端渲染。造草稿这一步不联网、不需要任何凭据：

```bash
pip install pyJianYingDraft
python build_draft.py --video clip.mp4 --title "开场标题" --seconds 3 --out ./drafts
python render.py --draft ./drafts/pjy-demo --cookie-file ./jy-cookie.txt --out ./out
```

第二步生成自包含草稿：素材拷进草稿目录、路径改写为占位符，不联网也不要凭据。第三步出片需要两个凭据，平台 `AuthKey` 从环境变量 `HTW_API_KEY` 读、剪映登录态从 `--cookie-file` 读。生成草稿的实际输出：

```
草稿已生成: ./drafts/pjy-demo
  画布 1920x1080@30  时长 3.0s
  拷入素材 1 个，改写路径 1 条
    materials/clip.mp4
```

草稿目录是自包含的（`draft_content.json` + `draft_meta_info.json` + `materials/`），不依赖本机绝对路径。这一步很容易被跳过，但云端不存在 `D:\素材\a.mp4`，不改写路径只会渲出黑屏。

想看滤镜清单与选型约束：

```bash
python build_complex.py --list-fx
```

输出里最关键的是这两行（清单共 240 条，只放行 25 条）：

```
滤镜 25 条可用（7 位短 effectId，2026-11-09 逐条云端 A/B 生效；总 240）：
另有 215 条不可用，不列入可选清单：19 位 effectId 会被云端静默忽略，VIP 同理。
```

示例里有一条细节值得单独说：复杂草稿落盘时，滤镜仍是**本仓内部旧形态**（19 位 `effect_id`、空 `path`、挂在视频段 `extra_material_refs` 上）：

```
filters[0] = {type: filter, name: 净透, resource_id: 7085360406423671303,
              effect_id: 7085360406423671303, path: ""}
```

走服务端导出接口时，会在上报云渲染前统一改写成官方形态（7 位短标识 `2938816` + 独立 `filter` 轨）。**如果你要自己直连云端，别照抄这份落盘草稿**，改写得自己做——第三节那张表就是给这种情况用的。

全部命令、真实输出、生成物结构、以及「秒 vs 微秒」「zip 体积等于源素材体积」「草稿结构版本」等几个坑，都在示例 README 的「示例展示」一节。

## 九、前提与限制（请先看完再动手）

- **两个凭据是两回事**：平台 `AuthKey` 用于提交任务（按成片时长计费，免费档每月 60 分钟、按月重置、有效期 30 天）；剪映登录态由**你自己的账号**提供，服务端只随这一次请求使用、用完不落盘，不代管、不轮换账号。没有对应权益，需要会员的功能照样渲不出来。
- **结论有版本边界**：以上形态对照与 25 条验证完成于 2026-11-09，对应 `app_version=11.5.1` / `sdk_version=15.7.0`。云端形态变更时，这份对照需要重做。
- **七种风格的端到端渲染没有逐条重跑**：机制（同一段形态改写）与资源（25 条逐条）分别有实测，「配置 → 生产草稿」这一段由无网络回归测试锁住。以后换任何一条资源标识、改改写函数或动出片链路，仍必须用生产链路做像素对照。
- **素材类型覆盖有限**：已验证的是多段拼接、转场、圆形蒙版、关键帧缩放、标题动画、字幕、双音轨、资源型滤镜。贴纸、视频特效、画中画、抠像、倒放、曲线变速等没有验证过。
- **自包含草稿要把素材一起打包**，zip 体积约等于源素材体积；5 分钟 1080p 大约 100–500MB。大素材建议先压短片试通。
- 第一次用建议先渲一条 5 秒短片确认画面，再上批量任务。

## 十、想要的是真实场景，不是一个 Star

这类静默失败最缺的不是又一个结论，而是**反例样本**。如果你手上正好有一条「渲出来了但没效果」的草稿，欢迎在仓库提个 Issue，带上三样东西就够：剪映 / 草稿版本、用的滤镜或特效名、一张按帧号抽出来的对比图。不会写代码也没关系，把场景描述清楚就很有帮助——我们现在更想知道的是「哪种真实场景会踩到」，不是有多少人点了收藏。

三层入口，按需取用：

- **在线体验**：<https://htwmedia.dpdns.org>（邮箱注册后直接申领 AuthKey）
- **桌面客户端**：[最新版本](https://github.com/HTWMedia/HTWClient/releases/latest)（v0.5.2 起，左侧「草稿体检」不联网、不校验 AuthKey、不消耗额度，能先看出这条草稿会不会渲出残片）
- **仓库与可复现示例**：<https://github.com/HTWMedia/HTWClient> · [`examples/pyjianying-draft/`](https://github.com/HTWMedia/HTWClient/tree/main/examples/pyjianying-draft) · [图文教程](https://github.com/HTWMedia/HTWClient/blob/main/guide-videos/out/使用说明.md)

完整的取证记录（含每一轮被推翻的假设、噪声基线、接口返回码）整理在项目的协议文档里，仓库示例目录也放了每条命令的真实输出。这篇里所有数字都来自实测成片抽帧，没有推算值。
