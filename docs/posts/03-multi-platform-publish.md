# 抖音 / 小红书 / B站 / 头条 一键发布：自建方案要解决的四个问题

> 关键词：多平台一键发布、抖音自动发布、小红书发布 API、自媒体分发工具自建

## 一、先想清楚：为什么要自建

市面上的分发工具不少，能用的也不少。自建的唯一理由是**你要把它接进自己的流水线**——成片在服务端生成完，直接进发布队列，而不是下载到本地再手工上传。

代价也很明确：**平台 Cookie 必须交给某个程序保管**。这不是自建独有的问题，用现成工具一样要交。区别只在于交给谁。

## 二、四个真问题

### 1. 「已配置」不等于「能发」

这是最容易埋雷的地方。用户在设置页填了 Cookie，界面显示「已配置」，但实际上：

- Cookie 可能早就过期（各平台有效期不同，抖音和小红书差别很大）；
- Cookie 格式可能对但缺关键字段（比如缺 `sessionid`）；
- 账号可能被限流，登录态正常但发不出去。

所以状态必须是**三态**而不是布尔：`true`（已验证可发）/ `false`（验证失败）/ `null`（从没验证过）。前端不能把 `null` 渲染成「已配置」——那是骗用户。

验证本身要花时间（每个平台一次真实请求），所以结果缓存 60 秒，避免每次进页面都串行打四个平台。

### 2. 一次提交，四个平台，可能部分失败

抖音成功、小红书失败、B站成功、头条超时——这是常态，不是异常。

设计上必须满足：

- 一次提交产生一个**父任务**，每个平台是**子任务**，各有独立状态；
- 重试只重试失败的那一个，不能整批重发（否则抖音会重复发）；
- 每个子任务有稳定的 `subTaskId`，重试时带它，而不是带平台名。

### 3. 发之前要拦一道

平台侧的合规检测是异步的、有时还不给原因。发出去再删，账号权重已经掉了。所以提交前自己先跑一遍：敏感词、绝对化用语、导流信息、二维码暗示。拦不住全部，但能拦掉大部分低级错误。

这一步的取舍是**延迟**：多一次模型调用，提交慢几秒。对日更作者可以接受。

### 4. Cookie 的存储比发布本身更危险

把 Cookie 存服务端，等于把账号的完整登录凭据交出去——它是可以直接登录的，不是限权 token。

三条底线：

- 只存必要平台的，不存全量；
- 提供「取回」和「清除」两个动作，让用户能自己撤销；
- 文档里**写清楚这件事**，不要用「安全加密存储」这类含糊话糊过去。

最后一条最容易被跳过。但用户发现「原来你存了我的登录态」的那一刻，信任就没了——不如一开始就说。

## 三、落地形态

```bash
# 提交发布（可只发部分平台）
node htw-skills.mjs call publish --submit \
  --title "标题" --content "正文" --tags a,b \
  --media-urls https://.../out.mp4 \
  --platforms douyin,xhs

# 查状态 / 重试单个平台
node htw-skills.mjs call publish --status <taskId>
node htw-skills.mjs call publish --retry <subTaskId>

# 只跑合规检测，不发
node htw-skills.mjs call publish --compliance --content "正文"
```

接口契约在 `agent/skills/htw-media-publish/references/api.md`，实现（MIT）：
<https://github.com/HTWMedia/HTWClient>

## 四、不适用场景

- **要 100% 稳定**：平台反爬策略随时变，任何第三方分发方案都会周期性失效，做好维护预期。
- **多账号矩阵**：本方案按账号存 Cookie，矩阵运营需要额外的账号隔离与调度层。
- **不接受托管凭据**：那就只能本机跑浏览器自动化，自己承担维护成本。
